# Methodology Decisions — v0.1 Contract

This document records the architectural and methodological decisions made
during the v0.1 design phase of `battery-diagnostic-robustness-demo`. Each
decision lists its rationale, its consequences for downstream code, and the
conditions under which it should be revisited in later versions.

This document is the single source of truth for v0.1 narrative consistency.
README, commit messages, CV bullets, and presentation slides shall not
contradict statements made here.

---

## 1. Project framing: signal-to-state, not physics-based

**Decision.** The project description and public-facing materials use the
phrase "signal-to-state diagnostic audit pipeline". The phrase
"physics-based" shall not appear in the project description or README until
runtime PyBaMM integration ships in v0.2.

**Rationale.** v0.1 generates battery profiles synthetically via a
parameterised 1RC equivalent circuit (see §2). No first-principles
electrochemistry is solved at runtime. Claiming "physics-based" capability
in v0.1 would constitute capability inflation. The "signal-to-state" framing
is more accurate and aligns with the conceptual thread shared with the
upstream DC–AC superimposed charging research:

> An observable signal is not automatically equivalent to the underlying
> physical state. The diagnostic question is whether simple rules can
> distinguish true state deviations from sensor-layer deviations and
> cell-to-cell scatter using only signal-layer evidence.

**Consequences.**
- README, repo description, and external communication use "signal-to-state"
  rather than "physics-based".
- This file (`docs/methodology_decisions.md`) may state factual data
  provenance — e.g., "OCV–SOC table pre-derived from PyBaMM Chen2020 as
  static offline reference data" — because such statements are
  data-provenance disclosure, not capability claims.
- v0.2 may upgrade to "physics-based" framing once runtime PyBaMM coupling
  ships.

**Reversibility.** Revisited in v0.2 when SPMe simulation enters the
runtime pipeline.

## 2. v0.1 synthetic profile model: 1RC ECM

**Decision.** v0.1 synthetic profiles are generated by a single-RC pair
equivalent circuit model:

```
V(t)        = OCV(SOC(t)) − R0 · I(t) − V_RC(t)
dV_RC/dt    = − V_RC / (R1 · C1) + I(t) / C1
SOC(t)      = SOC(0) − ∫ I(τ) dτ / C_nominal
```

Sign convention: positive current denotes discharge.

Higher-order ECMs (2RC, 3RC), full DAE physical models (DFN, SPMe), and
ad-hoc non-physical voltage curves are out of scope for v0.1.

**Rationale.**
- A pure-resistive (0RC) model lacks the polarisation decay needed to
  exercise OCV-reset diagnostic rules and pulse-rest behaviour.
- 1RC captures one dominant relaxation mode, sufficient to produce
  qualitatively realistic transient voltage responses.
- 2RC adds parameter-identification complexity without commensurate v0.1
  value.
- DFN/SPMe is the v0.2 upgrade path; using PyBaMM at runtime in v0.1
  violates the "no runtime PyBaMM coupling" boundary.
- The 1RC architecture is forward-compatible: v0.2 can replace empirical
  (R0, R1, C1) with values fitted from PyBaMM HPPC simulations without
  altering the surrounding pipeline.

**Consequences.**
- `src/bdr_demo/profile_generator.py` implements a 1RC integrator only.
- Per-case parameter perturbations apply to (R0, R1, C1) and the OCV–SOC
  table separately, allowing isolated fault injection.
- v0.4 model-based observer benchmark can use the same 1RC structure as the ground-truth
  model — a deliberate choice to make estimator-vs-truth analysis
  transparent.

**Reversibility.** 1RC is replaced by an SPMe-derived ECM in v0.2
(parameter re-fitting only, structural form retained). 2RC may be
introduced in v0.4 if EKF benchmarks require additional fidelity.

## 3. OCV–SOC data: pre-derived from PyBaMM Chen2020

**Decision.** The OCV–SOC table used by v0.1 is exported one time from the
PyBaMM Chen2020 parameter set (LG M50 21700, NMC811 + silicon-blended
graphite anode). The exported CSV (`data/ocv_chen2020.csv`) is committed to
the repository as static reference data.

**Rationale.**
- v0.1 runtime must not depend on PyBaMM (per scope contract).
- Hand-fitting an OCV polynomial would be either inaccurate or trivially
  textbook-derived — neither honest nor reproducible.
- Chen2020 is a published, peer-reviewed parameter set traceable to LG M50
  measurements, providing scientific grounding without overclaiming
  proprietary data.
- One-time offline export is a data-provenance act, not runtime coupling —
  this is the precise distinction between "synthetic profile generator" and
  "physics-coupled simulation".

**Consequences.**
- `scripts/export_ocv_table.py` is run once before v0.1 first use; it
  requires PyBaMM in the build environment but not in the v0.1 runtime
  environment.
- The exported CSV is committed; subsequent v0.1 use does not require
  PyBaMM.
- README states explicitly: *"OCV–SOC table is pre-derived from PyBaMM
  Chen2020 parameter set; v0.1 runtime has no PyBaMM dependency."*

**Caveat — Chen2020 (LG M50) vs MJ1 mapping.** Chen2020 represents the LG
M50 cell (21700 format, 5.0 A·h nominal). The upstream master's thesis
work uses LG INR18650 MJ1 (18650 format, 3.5 A·h nominal). v0.1 reuses
Chen2020's OCV(stoichiometry) curve (justified by shared NMC811 +
Si-blended chemistry family) while setting the v0.1 nominal capacity to
3.5 A·h independently. The OCV–SOC mapping therefore treats the OCV curve
as chemistry-family representative; cell-specific differences in
stoichiometry window are not captured. This simplification is documented
here and revisited in v0.2 if MJ1-specific OCV becomes relevant.

**Reversibility.** v0.2 may replace the OCV–SOC data with MJ1-specific
measurements or a different parameter set if research direction shifts.

## 4. Cluster topology: 24s1p pure series only

**Decision.** v0.1 implements a virtual battery module of 24 cells in pure
series (24s1p). Parallel branches, current redistribution among cells, and
electrochemical-electrical coupling are out of scope.

**Rationale.**
- Pure series eliminates the inter-cell coupled-circuit problem: each cell
  sees the same prescribed pack current, so individual-cell simulations are
  independent and trivially aggregatable.
- A 24-cell module size lies within the realistic range for automotive HV
  packs (e.g., approximately one quarter of a 96s string), large enough to
  demonstrate cell-to-cell scatter effects without becoming a
  dataset-engineering exercise.
- Parallel topology requires solving Kirchhoff's current law across
  branches with cell-impedance asymmetry — a non-trivial circuit solve
  best handled by tools such as `liionpack` (which is itself in
  maintenance mode and out of v0.1 dependency scope).
- The diagnostic question of interest (signal-to-state ambiguity under
  cell-to-cell scatter) is fully expressible in a series-only topology.

**Consequences.**
- `src/bdr_demo/module_aggregator.py` aggregates by sum
  (V_pack = Σ V_cell), with prescribed current and no inter-cell circuit
  solve.
- Per-case scatter is applied at the cell-parameter level prior to profile
  generation.
- Pack-level diagnostic rules see only V_pack and I_pack; cell-level
  ground-truth scatter is recorded in `module_inconsistency_report.csv`
  but is not exposed to diagnostic rules. This deliberate asymmetry is
  the observability problem v0.1 demonstrates.

**Reversibility.** Parallel and mixed topologies, together with current
redistribution, are deferred to a hypothetical v0.5+ if research
direction warrants. No v0.1–v0.4 milestone depends on this extension.

## 5. Baseline cell parameters (locked)

The following baseline parameters define the "healthy reference cell"
against which all perturbation cases are compared:

| Parameter | Value | Source / rationale |
|---|---|---|
| Nominal capacity, C_nom | 3.5 A·h | LG INR18650 MJ1 datasheet; upstream master's thesis cell |
| Nominal voltage, V_nom | 3.6 V | NMC chemistry, mid-SOC OCV |
| R0_baseline | 0.05 Ω | Order-of-magnitude consistent with HPPC measurements from upstream master's thesis on 18650 NMC cells |
| R1_baseline | 0.02 Ω | Placeholder; chosen so R1 < R0 (typical short-time polarisation < ohmic) |
| C1_baseline | 500 F | Chosen so τ1 = R1·C1 = 10 s (representative short-time RC mode in NMC pulse response) |

These values are not measurements of any specific physical cell. They are
demonstrator parameters chosen to produce qualitatively interpretable
transient voltage responses while keeping case-matrix perturbations
within ±50 % bounds physically plausible.

The 10-second time constant is a placeholder for v0.1 demonstrability and
is not a measurement-grounded MJ1 value. v0.2 may replace it with the
median tau_FG_eff measured in upstream HPPC audit (`pybamm-dcac-superimposed`
Day 17 audit results) once the SPMe-derived ECM-fitting pipeline is in
place.

## 6. Case matrix nomenclature corrections

Two case-label corrections relative to earlier draft case matrices:

| Earlier label | v0.1 locked label | Reason |
|---|---|---|
| `soc_offset_p05` | `initial_soc_mismatch_p05` | The injected fact is a physical-layer disagreement between the cell's true initial SOC and the BMS-assumed initial SOC, not an estimator algorithm bug |
| fault label `soc_estimation_bias` | fault label `initial_soc_inventory_offset` | "estimation bias" implies algorithmic error inside the BMS; v0.1 injects a SOC-inventory offset that the diagnostic rules must detect from external evidence |

These corrections matter because they propagate into
`observability_matrix.csv`, the verdict logic, and any external
description of what v0.1 demonstrates. Estimator algorithm bugs are
trivial to construct; cell-state inventory offsets are the genuine BMS
diagnostic challenge.

## 7. Diagnostic rules: demonstrator-level, not production BMS

v0.1 implements six rule-based diagnostic checks. Voltage sensor bias is
treated as an input-side perturbation (a case-matrix entry), not a
separate rule; its detection is the responsibility of the voltage-residual
rule below.

| # | Rule | Method | Verdict thresholds |
|---|---|---|---|
| 1 | Coulomb-counting drift | SOC_CC(t) = SOC_init + ∫I(τ)dτ / C_nominal compared with ground truth SOC | FAIL > 5 %; WARNING 3–5 % |
| 2 | OCV-reset consistency | Inverse OCV lookup at designated rest plateaus, compared with ground truth SOC | FAIL > 5 %; WARNING 3–5 % |
| 3 | Voltage residual | \|V_observed − V_1RC_predicted\| | FAIL > 100 mV; WARNING > 30 mV |
| 4 | Capacity consistency | C_inferred from a full discharge cycle compared with C_nominal | FAIL if C_inferred < 0.95 · C_nom |
| 5 | Contact-resistance proxy | R0 inferred from a step-current event compared with R0_baseline | FAIL if R0_inferred > 1.3 · R0_baseline |
| 6 | Module imbalance | max(V_cell) − min(V_cell) across the 24-cell module | FAIL > 50 mV; WARNING > 30 mV |

**Explicit framing.** These rules are demonstrator-level diagnostic
checks, selected for transparent traceability of *fault → signal →
verdict*. They are not production-BMS-grade algorithms. Model-based
observers (EKF, UKF) are deferred to v0.4. This framing is repeated
verbatim in README and in any results-section text.

**Threshold provenance.** Thresholds are demonstrator values chosen for
interpretability; they are not derived from any specific industrial
specification. Voltage sensor accuracy of 1–3 mV (typical industrial
specification) implies that the 30 mV voltage-residual warning threshold
sits well above sensor noise; the 10 mV sensor-bias case in the case
matrix sits below this threshold, deliberately producing an *ambiguity
case* that exposes the limits of residual-only detection — this is
itself one of v0.1's intended demonstrations.

## 8. Observability matrix: manually curated, not auto-generated

`observability_matrix.csv` lists, for each fault label in the case
matrix, qualitative descriptors of the fault's signature in voltage,
current, temperature, and SOC channels, together with an `ambiguity_level`
field.

**Decision.** In v0.1 this matrix is **manually curated** by the author
based on inspection of simulation outputs. It is not generated by an
automated signature-extraction algorithm.

**Rationale.** Defining "signature" rigorously (peak amplitude vs.
frequency content vs. time-domain pattern) and quantifying
"ambiguity_level" between fault classes are publication-grade research
questions in their own right. v0.1 treats the matrix as a design
document expressing the author's interpretation of the case matrix,
delivered in CSV form so that downstream programmatic use (e.g., the
verdict logic consulting `ambiguity_level` to flag low-confidence
diagnoses) remains possible.

**Consequences.**
- The CSV is hand-written and committed alongside source code.
- Each row is auditable against the corresponding case-matrix entry.
- v0.4 may automate signature extraction; this is a research extension,
  not a v0.1 deficit.

## 9. Forbidden vocabulary

The following terms shall not appear in the README, repo description,
public commit messages, CV bullets, or cover letters:

- `BMW`, `BMW-oriented`, `BMW PhD` — legal/branding cleanliness;
  decoupling from any specific employer narrative.
- `HIL`, `hardware-in-the-loop`, `Prüfstand`, `HIL emulator` — this
  project does not perform power-electronics emulation.
- `physics-based` — in v0.1 only; permitted in v0.2+ once runtime PyBaMM
  coupling ships.
- `production BMS`, `production-grade BMS algorithm` — the diagnostic
  rules are demonstrator-level.
- `real-time`, `real-time-capable` — PyBaMM/Python on a PC is not
  deterministic real-time; reduced-order model deployment is out of
  scope.

The phrase *"OCV–SOC data are pre-derived from PyBaMM Chen2020 as static
offline reference data"* is permitted in this file and in
internal documentation because it is a data-provenance disclosure, not a
capability claim.

## 10. Roadmap rationale

| Version | Scope | Why this stage |
|---|---|---|
| v0.1 | Synthetic 1RC profiles, 24s1p, six rule-based diagnostics, three reports, manually curated observability matrix | Establishes the diagnostic pipeline and the signal-to-state narrative without taking on PyBaMM runtime risk |
| v0.2 | PyBaMM SPMe profile bridge, 1RC ECM fitted from PyBaMM HPPC simulations | Upgrades the data source to PyBaMM-derived profiles while keeping the v0.1 diagnostic-rule interface unchanged |
| v0.3 | Bridge to `battery-testbench-simulator` via CSV interface, CAN-layer diagnostic verdict reuse | Demonstrates integration with the BMS message-layer testing framework without merging the two repositories |
| v0.4 | Automated observability matrix; EKF / UKF or comparable model-based observer benchmarks | Research-extension stage; pursued only if v0.1–v0.3 results justify it |

The roadmap is sequenced so that each version stands as a publishable
deliverable. The PyBaMM-DCAC research line remains the parent project
throughout; this demonstrator is a sibling, not a successor.

## 11. Relationship to upstream and sibling repositories

- **`pybamm-dcac-superimposed`** — physics-based simulation parent
  project, source of the methodological idea *"event/signal ≠ true
  state"*. v0.2 will draw the OCV table and HPPC pulse patterns from
  this project's PyBaMM scripts.
- **`battery-testbench-simulator`** — message-layer BMS testing
  framework. v0.3 will export profile CSVs in its
  `ScenarioBMSDataProvider` format and reuse its `Verifier` interface
  for diagnostic-verdict consistency. The raw-trace versus
  CAN-quantised-trace separation pioneered in that project informs the
  signal-to-state framing here, but no code is forked; the relationship
  is conceptual until v0.3.
- **`battery-charging-analysis`** — experimental-analysis tools
  (Δt(Q), Π/κ framework). Conceptually related but no direct code
  dependency.

The thread linking all four projects is the methodological observation
that **observable signals do not uniquely determine the underlying
physical state**. Each project instantiates this observation in a
different domain:

- DC–AC charging: voltage event ≠ state advancement.
- Diagnostic robustness (this project): sensor signal ≠ physical fault
  identity.
- Δt(Q) experimental analysis: pseudo-equivalent time ≠ true SOC
  equivalence.
